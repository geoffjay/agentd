# Installation Method

This document captures the plan for making agentd installable on production
hosts, not just developer machines.

## Problem

Today the only supported install path is `cargo xtask install-user`, which
requires `cargo`, the full source tree, and `bun`. That is fine for a developer
machine but unworkable for production systems where we only want to drop
prebuilt binaries and wire up services.

The release pipeline (`.github/workflows/release.yml`) already builds binaries
for `x86_64-unknown-linux-musl`, `x86_64-apple-darwin`, and
`aarch64-apple-darwin` on every `v*` tag and renames the user-facing `cli`
binary to `agent`.

## End state

A `curl … | sh` installer (generated by **cargo-dist**) that downloads the
release binaries for the host's platform, verifies them, places them on disk,
and then runs `agent install` to do the platform-specific setup. The
platform-specific logic stays in Rust (one source of truth) rather than being
reimplemented in shell.

## Phase 1 — `agentd-install` crate + `agent install` (this change)

Relocate the install/service/migration logic out of the dev-only `xtask` crate
into a reusable `agentd-install` library that the shipped `agent` binary can
call with no source tree and no `cargo`/`bun`.

- New crate `crates/install` (`agentd-install`): the `Platform` trait and the
  macOS (launchd) / Linux (systemd) implementations, the `SERVICES` registry,
  the `config.toml` gap-fill merge (`install_config`), and the migration runner
  (`migrate`).
- The only inputs that differ between dev and production are the *source*
  directories for binaries and UI assets, supplied via `InstallPaths`
  (`bin_src`, `bin_dir`, `ui_src`). The dev path passes `target/release` and
  `ui/dist`; production passes the directory where the installer placed the
  binaries.
- New CLI commands on the shipped binary: `agent install`
  (`--bin-src`, `--ui-dir`, `--skip-migrations`), `agent uninstall`,
  `agent service <start|stop|restart|status> [name]`, `agent migrate`, and
  `agent migrate-status`.
- `xtask` becomes a thin developer front-end: it still builds binaries
  (`cargo`) and the UI (`bun`), then delegates platform setup to
  `agentd-install`. `release` and `generate-entities` (which needs
  `sea-orm-cli`) remain dev-only in `xtask`.

## Phase 2 — cargo-dist + installer + release pipeline (future)

- Adopt [`cargo-dist`](https://opensource.axo.dev/cargo-dist/) to generate the
  `curl … | sh` installer, per-target tarballs, `SHA256SUMS`, and a release
  manifest from the existing tag-triggered workflow.
- The installer downloads + verifies + extracts binaries into a `bin` dir, then
  runs `agent install` for the platform/service/migration setup.
- Add `aarch64-unknown-linux-gnu` (or musl) to the release matrix — currently
  there is no Linux arm64 artifact.
- Optionally publish a Homebrew tap formula and `cargo-binstall` metadata
  (cargo-dist can emit both).

cargo-dist will not perform the launchd/systemd/migration setup — that stays in
`agent install`, which is exactly why Phase 1 is the prerequisite.
